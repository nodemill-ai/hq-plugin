# hq 태스크

사일로 → 로드맵 → 에픽 → 태스크 (`todo · doing · review · done`).

## 만들기
1. 말에서 뽑는다: 제목 · 사일로 · 담당 · 마감 (+ 에픽 · 고객사 · 시작일 · 설명 — 있을 때만). 설명은 § 글 쓰기대로 (액션 아이템 목록).
2. id 조회 (1회씩): `listSilos` · `listMembers { activeOnly: true }` (이름 또는 직책 `title` · 나 = `me: true` 행) · `listEpics` · 회사 이름이 나오면 `listCustomers` (표기 그대로 — "가나" → "가나금속" · 목록에 없으면 `customer` 를 넣지 않는다).
3. 빠진 값은 추천을 채운다: 사일로 = 말에 나온 영역 · 고객사 · 같은 주제 태스크의 사일로 / 담당 = 이름 · 직책이 나오면 그 사람, 아니면 본인 (`me` 행 — 누구냐고 묻지 않는다) / 마감 = 근거 있는 것 하나 — 말의 기간 계산 ("이번 주" = 금요일) · 관련 에픽 · 로드맵의 계획 끝 · 미팅 날짜 (다음 주간 미팅 전) · 태스크 크기 (잡일 · 연락 · 확인 = 1~3일 · 문서 · 개발 = 1~2주), 근거가 없으면 "마감 미정 (담당이 정함)" / 에픽 = 제목이 기존 에픽과 겹치면 그 에픽 (크기는 아래 「에픽으로 묶기」).
4. **확인 한 줄** — 실제 날짜로: "HQ 사일로 · 담당 홍길동 · 마감 2026-11-10 (추천 · 다음 미팅 전) — 이대로 만들까요? (바꿀 것만 말해 주세요)". 추천한 값은 "(추천)" 표시 · 마감 추천은 "(추천 · 근거 한 단어)". 사용자가 마감을 말하지 않았으면 이 한 줄에서 반드시 묻는다. 사용자가 전부 말했어도 이 한 줄은 거치고, 값을 바꾸면 고친 한 줄을 다시 보인다. "다음 금요일" 처럼 두 날짜로 읽히면 확인 한 줄에 둘 다 적어 고르게 한다. 설명을 썼으면 확인 한 줄 아래에 그 설명 본문을 그대로 보인다 (확인은 한 번).
5. "ㅇㅇ · 좋아 · 그렇게" → `createTask { title, siloId, assigneeId, dueDate | duePending: true, epicId?, customer?, startDate?, description? }`.
6. 보고: `HQ-0042 — 제목 / 사일로 / 담당 / 마감` 한 줄.

## 에픽으로 묶기
- 에픽 = 한 가지 결과물로 끝나는 태스크 4~5개 묶음. 진행하다 관련 태스크가 붙는 것은 괜찮다.
- 기존 에픽에 붙이기 전에 `listEpics` 의 `progress.total` 로 현재 개수를 본다. 8개쯤 넘거나 주제가 달라지면 붙이지 않고 새 에픽을 제안한다 (같은 로드맵 아래 하나 더).
- 새 에픽: `createEpic { siloId, name, roadmapId?, startDate?, endDate? }` — 확인 한 줄 뒤.
- 넓은 요청을 쪼갤 때는 에픽 하나에 다 넣지 않고 결과물 단위로 에픽을 나눈다.

## 조회 — "내 할 일 뭐 있어" · "홍길동 할 일" · "이번 주 마감" · "가나 건 뭐 있어"
- `listTasks { mine?, assigneeIds?, dueWithinDays?, customer?, status? }` → 한 줄씩 `키 제목 (마감)`. 내 것 = `mine: true` · 다른 사람 · 여러 명 ("나랑 홍길동") = `listMembers` 의 id 로 `assigneeIds`. 담당 이름은 `listMembers`. 마감으로 묻는 조회 ("이번 주 마감") 는 결과에서 `status: done` 을 뺀다 (끝낸 일도 계획 마감이 남는다).

## 수정 — "HQ-12 마감 다음 주 금요일로" · "담당 철수로" · "제목 바꿔"
1. `getTaskByKey { key: "HQ-0012" }` → 바뀔 값 한 줄 확인 (설명을 바꾸면 그 아래에 새 설명 본문) → `updateTask { taskId, <바꿀 필드만> }` (`null` = 비움 · 마감을 넣으면 마감 미정이 풀린다).

## 댓글 — "HQ-12 에 '…' 댓글 달아" · "HQ-12 에 ~ 했다고 댓글 달아"
- 따옴표로 준 문장 = 한 글자도 바꾸지 않고 바로: `getTaskByKey` → `addComment { taskId, body }` (만든 사람 · 담당에게 알림).
- 요지만 말했으면 = `getTaskByKey` (제목 · 설명이 맥락) → § 글 쓰기대로 풀어 쓴 본문을 보이고 "이렇게 달까요?" → 좋다고 하면 `addComment` · 고치라고 하면 고친 본문을 다시 보인다.

## 확인 요청 — "HQ-12 대표님한테 확인 요청해 줘 — …" · "확인했다고 해 줘" · "내가 보낸 요청 확인됐어?"
- 보내기: `getTaskByKey` → 받을 사람 = `listMembers { activeOnly: true }` 의 id (이름 · 직책 · 여러 명 가능 · 나는 빼고) → 확인 한 줄 ("HQ-0012 에 대표 · 홍길동에게 확인 요청을 보낼까요?") + 그 아래 본문 (따옴표면 그대로 · 요지면 § 글 쓰기대로 풀어 쓴 것) → `addComment { taskId, body, requestTo: [id…] }`. 무엇을 · 왜 확인해 달라는지는 본문에 담는다.
- 확인: `listRequests` 의 받은 것에서 그 요청 (`commentId`) 을 찾아 → `acknowledgeRequest { commentId }` · 답을 함께 말했으면 `reply` — 따옴표면 그대로 바로 · 요지면 풀어 쓴 답을 보이고 확인 뒤.
- 조회: `listRequests` → 보낸 것은 사람별 확인 여부 ("2명 중 1명 확인 · 홍길동 아직 · 3일 전 요청"). 확인 취소 · 요청 취소는 hq 웹에서만 된다고 안내한다.

## 상태 — "시작했어" · "검토 올렸어" · "끝났어"
- `changeTaskStatus` doing · review · done. 날짜는 상태가 맞춘다 — 따로 `updateTask` 하지 않는다. 다른 사람이 바꾸면 만든 사람에게 상태 변경 알림이 간다.
- 끝낼 때: 한 일이 설명과 달라졌으면 `updateTask { description }` 으로 실제 한 것을 § 글 쓰기대로 다시 쓴다 (첫 줄에 무엇을 했고 결과가 어땠는지 · 그 아래 한 일 목록 · 남은 일은 넘긴 태스크와 함께 · 계획 항목은 한 일로 바꾸고 하지 않은 것은 지운다 · 새 설명을 보이고 확인 뒤). 마감은 고치지 않는다 — 계획 마감으로 남고 실제 끝은 완료 시각 (`completedAt`) 에 기록된다.
- **검토** 는 상태일 뿐 확인 요청이 아니다 — 누가 확인해야 하면 위 「확인 요청」 으로 보낸다.
- `closeEpic` 이 열린 태스크 키 목록과 INVALID 를 주면 목록을 보여 주고 확인 뒤 `force: true`.

## 글 쓰기 — 설명은 목록 · 댓글 · 확인 요청 · 답은 풀어 쓴 말
- 태스크 설명 (본문) 은 액션 아이템과 업무 목록으로 쓴다. 첫 줄에 무슨 일인지 (어디서 나온 일인지 포함) 한두 줄, 그 아래에 묶음 제목 (묶음이 여럿이면 번호) 과 `- ` 항목을 둔다. 항목은 한 줄에 할 일, 확인할 것, 받을 것, 결정할 것 하나씩 짧게 쓰고 명사형이나 평서형으로 끝낸다 (`~ 확인` · `~ 전달` · `~ 로 변경한다`). 해요체로 풀어 쓰지 않는다. 경과, 논의, 배경 이야기는 설명에 쌓지 않고 댓글로 단다. 설명은 쓴 그대로 보인다 (마크다운 아님) — `#` 제목, `**`, 표, `- [ ]` 를 쓰지 않는다.
- 댓글, 확인 요청, 답은 처음 읽는 사람이 회의록이나 대화 없이 그 글만 읽고 이해하게 풀어 쓴다. 해요체 문장으로 쓰고 명사로 끝내지 않는다. 어디서 나온 일인지, 왜 하는지, 지금 상태, 무엇을 하면 끝인지, 언제까지인지 (안 정했으면 그렇다고), 다음에 누가 무엇을 하는지 (남은 일이 없으면 없다고) 를 넣는다. 기호 (`·` `→` `=` `/` `—`) 로 낱말을 이어 붙이지 않고 말로 잇는다 (늘어놓을 때는 쉼표나 `와`, `과`). 길이는 필요한 만큼 쓴다.
- 설명과 댓글 모두, 처음 읽는 사람이 모를 수 있는 번호, 키, 파일, 화면, 도구 이름, 내부 용어는 무엇인지, 어디인지 함께 쓴다. 일에 대한 사실 (날짜, 금액, 이름, 결정, 이유) 은 원문에 있는 것만 쓴다.
- 사용자가 따옴표로 준 문장은 그대로 쓴다 · 요지만 말했으면 쓴 글을 먼저 보이고 확인 뒤 쓴다.
- 규칙 하나씩 · 전 · 후 예 = `references/글-쓰기.md`.

"마바상사 소개서 자료 모아 줘" → "제목 '마바상사 소개서 자료 수집' · 영업 사일로 (추천) · 담당 나 (추천) · 마감 2026-11-06 (추천 · 자료 수집 1~3일) — 이대로 만들까요? (바꿀 것만 말해 주세요)"
"HQ-0042 에 담당자 연락처 받았고 다음 주 화요일에 통화하기로 했어 — 댓글 달아" (태스크 제목 `○○ 연동 담당자 연락처 · 가능 여부 확인`) → "HQ-0042 에 이렇게 달까요? — '○○ 연동 담당자 연락처를 받았어요. 다음 주 화요일에 통화해서 연동이 가능한지 확인할게요.'" (`○○ 연동` · `가능한지 확인` 은 제목에서 온 말 — 말하지 않은 날짜 · 결과는 넣지 않는다)

## 규칙
- 지금은 못 하고 조건을 기다리는 일 ("언젠가" · "~ 되면") 은 태스크로 만들지 않고 보류함 (`parking` 스킬) 에 넣는다 — 마감 미정은 곧 할 일인데 날짜만 모를 때.
- 확인 한 줄 없이 `createTask` · `updateTask` 하지 않는다.
- 같은 요청으로 두 번 만들지 않는다 — 실패 여부를 모르면 `search` 로 제목을 먼저 찾는다.
- `deleteTask` · `closeEpic` 은 사용자가 명시했을 때만, 키 · 제목 확인 뒤.
- 공통: id 는 조회로만 얻는다 · `FORBIDDEN` = admin 에게 요청 안내 · 401 · 연결 오류 = "hq 다시 로그인 (Code `/mcp` · claude.ai 플러그인 Connectors 탭)" 안내 후 멈춤 · 결과 JSON 을 붙이지 않는다.
